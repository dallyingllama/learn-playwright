First-Time Setup After Clone

Run from the repository root:

corepack enable
corepack prepare pnpm@10.9.0 --activate
corepack pnpm install
corepack pnpm exec playwright install

First 10 Minutes

corepack pnpm run test:spec:dev tests/login.spec.ts
corepack pnpm run show-report

Environment Selection (TEST_ENV)

Test scripts select environment files through TEST_ENV:

  • dev → .env/dev.env

  • test → .env/test.env

  • e2e → .env/e2e.env

Examples:

corepack pnpm run test:dev
corepack pnpm run test:test
corepack pnpm run test:e2e

Key Dependencies and Why They Exist

  • @playwright/test: browser automation test runner and assertion API used by this repo.

  • typescript: static type checking for tests, page objects, data, and utilities.

  • cross-env: cross-platform environment variable support in npm scripts (for example TEST_ENV).

  • dotenv: loads environment variables from .env/<name>.env via playwright.config.ts.

  • @faker-js/faker: generates realistic test data for forms and table scenarios.

  • antora: builds and assembles the publishable documentation site.

  • live-server: previews generated Antora docs output from docs/antora/build/site/.

  • ejs: templates report index content used by GitHub workflow helper scripts.

Unit Tests in This Repo

This repository uses both end-to-end tests and unit-style tests.

Unit-style tests live under tests/unit/ and focus on repository-owned logic (for example helper functions, metadata contracts, and data shape rules).

When unit tests make sense:

  • shared helper logic with branching (example: utils/gotoHelper.ts)

  • reusable utility behavior used by multiple specs

  • metadata and data-contract validation that should fail fast

When unit tests usually do not add value:

  • thin page-object wrappers that only click/fill once

  • flows already validated as user behavior in E2E coverage

  • checks that duplicate full browser workflows without adding faster feedback

Current implementations:

  • tests/unit/goto-helper.unit.spec.ts

  • tests/unit/annotations.unit.spec.ts

  • tests/unit/section-metadata.unit.spec.ts

  • tests/unit/checkbox-data.unit.spec.ts

  • tests/unit/fake-data-generators.unit.spec.ts

Typecheck (TypeScript Safety Check)

corepack pnpm run typecheck

Run typecheck:

  • after TypeScript changes in tests/, page-objects/, data/, or utils/

  • before commit

  • before opening or merging a PR

This checks types only and does not run tests.

Git Command Helpers

Common local git commands used during normal development:

git status -sb
git add <file-or-folder>
git add -A
git rm <file>
git add --renormalize .
git commit -m "short summary"
git pull --rebase origin main
git log --oneline -n 10

Quick usage notes:

  • Use git status -sb before and after test runs to confirm only expected files changed.

  • Stage specific files with git add <file-or-folder> to keep commits focused.

  • Use git add -A when your change includes newly created files together with edits/deletions.

  • Use git rm <file> when a file should be removed from both the working tree and git tracking.

  • Use git add --renormalize . after line-ending rule changes (for example .gitattributes) to restage files with consistent EOL normalization.

  • Use short commit messages that describe one logical change.

  • Rebase on origin/main before opening a PR when your branch is behind.

Navigation Pattern

  • tests/navigation.spec.ts is the explicit place where both navigation methods are tested directly.

  • In most other feature specs, navigation is setup rather than the behavior under test.

  • For shared page objects using gotoHelper:

goto() = deterministic default navigation goto.viaMenu() = explicit menu navigation goto.viaDirectLink() = explicit direct-link navigation goto.random() = explicit randomized navigation

Current repo pattern:

  • use deterministic navigation where the test demonstrates navigation behavior

  • use randomized navigation in feature specs when navigation is setup

  • keep randomized behavior explicit rather than hidden in default goto()

Current CI Behavior

  • GitHub Actions runs unit tests first as a fail-fast gate.

  • If unit tests pass, GitHub Actions runs the @sanity tests.

  • If the sanity stage passes, the workflow runs the full e2e suite.

  • If the sanity stage fails, the full suite is skipped.

  • The workflow publishes one report/history entry per run:

    • sanity report if sanity fails

    • full-suite report if sanity passes and the full run completes

  • The workflow ends in a failed state if either the sanity stage or the full suite fails.

Alerts Timing Note

  • tests/alerts.spec.ts contains one intentional timing assertion.

  • The timed alert scenario verifies that the alert does not appear immediately and then appears within the expected delay window.
